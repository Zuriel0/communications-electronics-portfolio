Concurrent log monitor via SSH.

One MAC address. Multiple possible destinations. A command-line tool that brings remote log searches into a single operational view.

I developed the monitoring tool to search across web and authentication logs from Ubuntu. This case study describes the design and workflow from my project account.

Outcome
Finding a request without knowing its destination.

A load balancer decides which web server handles an incoming request. When investigating a specific MAC address, the operator cannot know in advance which server holds the relevant event. Checking each machine separately divides the investigation across multiple log sources.

The engineering challenge

Observe every possible web destination while retaining visibility into authentication. A web match should identify the source without ending RADIUS supervision.

Business order and monitoring order are different.

The documented business flow moves from a successful web operation to RADIUS authentication. Observation spans both domains concurrently, through independent Web and RADIUS monitoring groups. Starting both observers does not make the business transaction itself parallel.

Local orchestration. Distributed observation.

The tool runs in an Ubuntu terminal. Bash coordinates the documented workflow, SSH provides remote access, and external configuration defines the targets, connection parameters and optional Web policy. Matches return to a central console with their source identity.

Input: validate and normalize the MAC address before preparing the search.
Coverage: monitor six web servers concurrently and one configured RADIUS server from two available targets.
Independence: keep the Web and RADIUS observation groups separate.
Output: retain server origin, source type and the matching log line in one console.
The boundary between the tool and its environment.

The local side contains the operator, configuration, orchestrator and console. The remote side contains the SSH connections and log sources being observed. The monitored service infrastructure is the project’s operating context.

From a MAC address to a traceable match.
Prepare the search

Receive, validate and normalize the MAC. Load the server inventory, active RADIUS target, connection parameters and Web policy.

Observe the remote sources

Prepare the search patterns and initiate concurrent SSH-based log monitoring across the Web group and selected RADIUS target.

Keep the source attached

Bring matching lines into the console with the server identity and source type, so centralization preserves their origin.

Apply the optional Web policy

Keep monitoring the web server that matched and stop the other web searches when this policy is enabled. RADIUS monitoring continues independently.

A policy for searches

Narrowing the Web group concerns monitoring sessions, not shutting down web servers. It does not change the authentication service or imply automatic RADIUS failover.

Input and configuration precede observation. Concurrency describes remote monitoring, rather than every operation in the tool.

Decisions that preserve visibility.
Search the possible destinations
Concurrent Web observation addresses the uncertainty of load balancing. The operator does not need to choose the correct web server before starting the search.
Keep observation domains independent
A match can narrow Web monitoring without removing the authentication view. The optional policy has a defined boundary: other Web searches, not RADIUS.
Make the active target configurable
The documented design selects one RADIUS server for each run. Two available targets support a configurable choice; this is not a claim of automatic failover.
Centralize without losing origin
A single console gathers the matches while retaining the server and source type. Consolidation remains useful because an event can still be traced to its source.
Implementation scope.

The project account describes a Bash tool on Ubuntu, with remote log observation over SSH and externally defined server selection and policy. My contribution described here is the monitoring tool.

Technology in context

Bash provides automation; Ubuntu is the local execution environment; SSH connects the local tool to remote sources. RADIUS identifies the authentication domain. React Flow powers this case study’s diagrams, rather than the command-line monitor.

One operational view, with the source intact.

The reported outcome is a centralized search workflow in place of separate manual server checks: MAC-related matches, their source servers and the Web/RADIUS context can be reviewed together.

This is a qualitative outcome from my project account, rather than a timed diagnostic benchmark or a measured reliability claim.

Skills demonstrated in the project

Shell automation, remote observation over SSH, MAC-oriented troubleshooting, monitoring policy design and technical architecture communication.

Design takeaway

Business sequence, concurrent observation and independent supervision describe different responsibilities. Making those boundaries explicit is central to reading this architecture correctly.
